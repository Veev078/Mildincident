# Existing-table claim safety review

This work hardens a **local, unconnected integration contract**. n8n remains the production authority. No schema, row, workflow, credential or deployment was changed, and no production concurrency experiment was run.

## Changes and evidence requirements

`src/n8n/claim-contract.js` still targets the existing `production_packages` row and three proposed claim columns. Claim inputs are bounded plain records; IDs, package versions, execution owner and SHA-256 digest are checked without string coercion. Accessors and unexpected fields are rejected. Returned row ID/story/version/owner/digest/state must match exactly.

The proposed atomic update retains `production_version` through **every transition**. If the package changes after a claim, the old owner cannot silently confirm or release the newer row. The claim stays blocked for explicit review. An uncertain claim never expires or resets automatically.

`transitionPackageClaim(repository, input, nextState, evidence)` now requires a fourth argument for transitions that authorize creation, release or success. Evidence must be generated by trusted source/provider adapters, never accepted as assertions from an HTTP request. Every proof is scoped to row ID, story ID, package version, execution owner and digest, with an observation within one minute (five seconds of future clock tolerance).

| Transition | Required normalized evidence |
| --- | --- |
| `reserved → create_started` | `kind: current_package`; freshly recomputed current-package digest, not a value copied from the claim |
| `reserved → idle` | `kind: pre_provider_failure`, `remoteRequestStarted: false`, bounded failure code; release is only valid before a provider request |
| `create_started → needs_reconciliation` | No success proof required; retaining an uncertain claim must remain possible |
| `create_started/needs_reconciliation → confirmed_draft` | `kind: independent_provider_readback`; candidate ID captured by the durable ledger; exact expected channel/caption and ordered media URLs; provider status `draft`, explicit `dueAt: null`, `sentAt: null` |

Read-back evidence contains `post`, `expectedChannelId`, `expectedCaption` and `expectedMediaUrls`. `input.candidatePostId` must match the independently returned post ID. The adapter must derive the expected caption/URLs from the source snapshot bound to the claim digest and use the candidate ID already persisted before read-back. A caller-created boolean or create response is insufficient. URL matches are not provider-side checksum verification, and no rights approval is inferred.

These checks prevent accidental transitions without evidence; they do not authenticate an untrusted adapter's claims about what it read. The integration boundary must keep proof creation server-side and use the existing source/provider connections. No public mutation endpoint or live adapter is supplied.

## Read-only audit boundary

`n8nReader` accepts only explicit workflow, execution and table/row GET paths needed by the existing audits, with bounded allowlisted query parameters. Encoded traversal, webhook routes, activate/retry operations, arbitrary resources, duplicate parameters and control characters fail before credentials are sent. Redirect following stays disabled, and redirected/different-resource responses are rejected even from an injected transport. Provider error bodies and rejected input values are omitted from errors.

## What still prevents production activation

The prior sprint's privately retained upstream source shows filtered `UPDATE … RETURNING` inside a transaction on its Postgres path. That source came from a moving upstream branch. It does **not** identify this n8n Cloud deployment's version/engine, guarantee its response semantics, or prove all concurrent clients use the same authority.

The minimum release evidence remains:

1. Identify the deployed n8n version and storage implementation from supported instance information or platform documentation. Pin the matching upstream revision and inspect the conditional-update/return-data path. An API key or successful read alone proves none of these properties.
2. Obtain approval for an isolated conditional-update experiment and any temporary schema/test workflow it requires. On one dedicated existing test row, run competing owners with the same expected state/version; confirm exactly one affected row and one owner. Verify that the loser receives **zero changed rows**, rather than a pre-update selection or unconditional success.
3. Test stale versions/digests, zero/multiple matches, source edits during work, crashes before/after provider intent, retry, and both known/unknown remote IDs. Use generated test assets and no publication/scheduling operation.
4. Review a separate migration proposal for the three claim columns. Seed every story with prior/uncertain handoffs as blocked. Preserve all history and existing Buffer mappings; do not initialize from an incomplete scan.
5. Make all existing create entry points use this same authority and a current-package read. Verify credential mapping and read-back against the actual provider before activation. Keep the release disabled until founder approval and all technical checks pass.

No new database/service is proposed. Local SQL tests validate the protocol and error paths only; they are not a remote atomicity claim. The package/table conditional update must be proven on the deployed backend before it can replace the current insert-then-read claim.

## Validation in this sprint

The targeted audit and claim suites pass **12 tests** covering accepted read paths, encoded traversal/action rejection, redirect mismatch, one winning SQL contender, stale versions, owner conflicts, evidence gates, media/caption/schedule mismatch and bounded/coercion-safe inputs. Tests use generated fixtures and a local SQL engine, with no network or production operation.
