# Contextual concept confirmation

Finish Post now distinguishes pending concept approval, an already-approved concept with an invalid stage, stale edits, development-only identity, and an ambiguous/incomplete production record. Only a genuinely pending canonical concept offers **Approve this concept & continue**. Existing concept approval is never inferred from photos, a local review, or a package error.

The explicit confirmation uses a restricted entry in the **existing** Founder / Concept Approval workflow (`77xnMJZ4bzo4VCVX`). The local patch reuses its canonical conditional story write, saved-state verification, review-token rotation and decision audit. The dedicated existing JWT credential, body hash, expiry, request identity, exact row/update version and concept-only intent are required. The Studio branch returns immediately after the audit and cannot reach automatic media sourcing, models, rendering or publishing. Legacy form behaviour remains on its existing branch; its conditional write gains an updatedAt condition. No new workflow, table, provider credential or publishing authority is created.

Studio records the in-flight intent in the existing transfer-event history. Lost replies reconcile the canonical story and matching native audit marker, without resubmission. Local edits are rebased only after independently verifying the concept-only update and unchanged content/version. Finish Post then resumes its existing preparation path. Pending native preparation is reconciled before stale-edit detection so its own save does not strand the journey.

## Evidence

- Isolated desktop/mobile Chromium: Build → Finish Post → explicit concept confirmation → canonical decision simulation → private native preparation simulation. One decision, one preparation, preserved caption/selection, refresh does not reapprove, zero Buffer/AI operations.
- Validation tests reject stale/foreign rows, non-concept intent, published concepts and malformed production state. Actual retained canonical node configuration was inspected; the local patch compiles against that snapshot.
- This is not live activation or live canonical acceptance. No story was approved in the live system.

## Activation boundary

The current private preparation workflow intentionally cannot approve concepts. A code-only deployment must not pretend otherwise: without the verified canonical binding, the contextual action explains that its connection needs activation and remains disabled.

Before deployment/installation approval, capture the **current** saved/active concept workflow, generate/review the patch against that exact baseline, verify persisted checksum and policy binding, and permit only `operations.conceptApproval` alongside private preparation. Policy also pins the canonical workflow ID/version/hash. Keep Buffer, public staging and paid AI disabled. Do not use the retained November baseline or its generated checksum as authorization to install. No founder-run Shell commands or manual concept operations are part of the ordinary journey.

An approved concept with an invalid stage or a malformed production record is identified as that specific condition, not offered another concept approval or silently normalized. Such records still require canonical reconciliation; this change does not invent a valid stage or duplicate a package.
